# 문제풀이 입문 설명 저작

이론을 읽었지만 문제풀이 경험이 부족한 학생에게 실제 첫 줄부터 완성 답과 검산까지 설명해요. 기존 카드의 풀이를 길게 바꾸는 것으로 끝내지 말고, 왜 그 개념을 떠올리고 왜 각 보기를 그렇게 판정하는지 밝혀요. 기출 합본·웹과제·교과서·강의노트·기존 정리노트의 관련 페이지를 먼저 확인해요. STT는 필요한 경우 보조로 사용하고 수업 밖 보충은 표시해요.

각 `explanations/pN.html`은 다음 직계 구역을 각각 하나 포함해요. 본문 답은 모두 펼쳐요.

| data-explanation | 작성할 내용 |
|---|---|
| understand | 주어진 조건과 구할 것을 내 말로 읽어요. 부정형이면 질문 방향을 굵게 적어요. `layer eli5` |
| recall | 문제의 단서 → 개념의 뜻 → 원리·규칙과 기호 → 적용 조건과 선택 이유. `layer formal` |
| start | 종이에 쓸 실제 첫 문장·표의 첫 행·교배표의 첫 칸, 필요한 개념 |
| solve | 보기마다 맞아요/틀려요 판정과 근거 개념, 마지막에 답. `layer formal` |
| verify | 완성 답과 다른 경로의 확인(소거·교과서 쪽 대조·교배표 재계산 등) |
| pitfall | 이 문항에서 하기 쉬운 오류. `layer warn` |
| retry | 설명을 닫고 수행할 1~3개 체크리스트. 항목마다 `<li>` 하나(`<ul><li>…</li></ul>`) |

표 순서대로 일곱 구역을 작성해요. recall의 제목은 **이 문제를 봤을 때 떠올릴 개념과 공식**이에요. 개념 이름만 나열하지 말고, 문제의 어떤 표현·조건이 그 개념을 떠올리게 하는지부터 설명해요. 영어 전문용어, 각 기호·용어의 뜻, 원리가 성립하는 조건과 이 문제에 적용하는 이유를 입문형으로 연결해요. recall은 일반 개념을 고르는 과정이고 start는 주어진 지문·보기로 종이에 적는 실제 첫 줄이에요. 긴 설명을 두 구역에 복제하지 않아요.

```html
<div class="layer formal" data-explanation="recall">
  <h4>이 문제를 봤을 때 떠올릴 개념과 공식</h4>
  <p>‘H⁺가 ATP 합성효소를 거치지 않는다’는 단서에서 화학삼투(chemiosmosis)를 떠올려요.</p>
  <p>전자전달계가 H⁺를 막 사이 공간으로 퍼내 농도 기울기를 만들고, H⁺가 ATP 합성효소(ATP synthase)를 지나 돌아올 때 그 에너지로 ADP와 인산에서 ATP를 만들어요.</p>
  <p>그래서 H⁺가 다른 길로 새면 전자전달은 계속되어도 ATP 합성이 줄어드는지부터 확인해요.</p>
</div>
```

공통 개념은 한 번 설명하고, 서로 다른 개념을 요구하는 소문항은 (a), (b)처럼 구분해요. 개념 수를 고정하지 않아요. 계산이 필요 없는 정성 문항에서는 정의·판단 기준과 근거를 설명하고, 유전 계산 문항에서는 대립유전자 기호와 비율 공식을 설명해요. 우측 sum에 `summary-group`을 추가해 `<h4>떠올릴 개념·공식</h4>` 아래 핵심 개념을 짧게 적어요. 본문 전체를 요약에 복제하지 않아요.

## 보기 판정

solve는 보기마다 한 문단씩 `<p>(n) 맞아요/틀려요 + 근거 개념</p>` 형식으로 판정해요. 틀린 보기는 어느 부분이 왜 틀렸는지, 맞는 보기는 어느 개념과 일치하는지 한 줄로 밝혀요. 판정이 끝난 뒤 마지막 문단에 답을 써요. 판정 문단은 보기 라벨(`(n)`, `A`, `ㄱ`)로 시작해요. 화면에서는 라벨로 시작하는 판정 문단마다 보기별 카드로 보이고, 결론 문단은 카드 밖에 남아요. 왼쪽 문제 패널에서 보기를 누르면 이 카드로 이동해요.

- **ㄱㄴㄷ형**: 진술 ㄱ, ㄴ, ㄷ을 각각 맞아요/틀려요로 먼저 판정하고, 맞는 진술의 조합과 일치하는 보기 번호를 고른 뒤 답을 써요. 조합 보기를 진술 판정 없이 바로 고르지 않아요.
- **부정형**("틀린 것", "아닌 것", "옳지 않은 것"): understand에서 질문 방향을 `<strong>`으로 굵게 적어요. solve에서는 다른 보기와 마찬가지로 맞아요/틀려요로 판정하고, 답은 **틀려요**로 판정된 보기라는 점을 마지막 문단에서 다시 밝혀요.
- 유전 계산: 부모 유전자형과 생식세포를 쓰고 교배표(Punnett square)나 곱셈 규칙으로 비율을 구해요. 표의 각 칸을 생략하지 않아요.

verify는 소거(남은 보기가 하나인지), 교과서 쪽 대조(해당 장 PDF의 쪽 번호), 교배표 재계산(다른 방법으로 다시 센 비율) 중 하나 이상으로 답을 다른 경로에서 확인해요. solve의 판정을 그대로 되풀이하는 것은 검산이 아니에요.

`source.json`의 subparts가 a,b이면 **solve와 verify 모두** 각각 아래 표지를 한 번씩 사용해요. 단일 문항도 `main` 표지가 필요해요. 보기 목록(`ul/ol.choices`)은 소문항이 아니에요.

```html
<div class="layer formal" data-explanation="solve">
  <h4>왜 이렇게 푸는지 함께 따라가요</h4>
  <div data-subpart="main">
    <p>(1) 틀려요. 근거 개념을 써요.</p>
    <p>(2) 맞아요. 근거 개념을 써요.</p>
    <p>따라서 답은 (2)예요.</p>
  </div>
</div>
<div class="layer formal" data-explanation="verify">
  <h4>완성 답과 검산</h4>
  <div data-subpart="main"><p>답 (2). 다른 경로로 확인한 결과를 써요.</p></div>
</div>
```

`~해요` 체와 영어 전문용어 병기를 사용해요. 기존 원문·조건·질문·보기·그림은 조립기가 붙이므로 재작성하지 않아요. 기출 원문은 조립기가 문제 안에 "기출 원문 보기"로 접어 보존해요.

마지막에 직계 `<div class="sum" hidden>` 하나를 넣어 시작·핵심 판단·검산을 요약해요. 이 요약만 UI의 우측으로 이동해요. 본문 hidden/details, 인라인 style, 실행 코드와 on* 속성은 사용할 수 없어요. 수식은 `$...$`/`$$...$$`, 그림은 저장소 내부 파일 상대경로나 정적인 inline SVG를 사용해요. 소문항 표지를 임의로 합치지 않아요.

개념 링크는 실제 존재하는 정리노트의 문항/토픽 anchor만 연결해요. 조각의 상대 링크와 그림은 입력 카드 HTML의 디렉터리 기준이에요. 정성 문항은 판단 기준과 근거를 확인하며, 한두 사례가 맞는다는 것으로 일반 진술이 맞다고 쓰지 않아요.

## 수식과 여백

짧은 수식은 문장 안에 두고 수식마다 스크롤 컨테이너를 만들지 않아요. 여러 행렬 답은 각각 독립된 줄에 배치해요. 긴 유도는 의미가 유지되는 등호·항을 기준으로 여러 식으로 나눠요. 한 수식의 여러 줄이 필요하면 `aligned`를 사용하고 수식 내용을 생략하지 않아요. 원문은 다시 쓰지 않고 템플릿의 표시 규칙으로 배치해요.

요약은 `<div class="summary-group"><h4>첫 줄</h4><p>...</p></div>`처럼 의미별로 묶어요. 제목과 내용 사이는 12px, 요약 그룹과 설명 구역 사이는 24px, 소문항 사이는 16px인 템플릿 규칙을 사용해요. 간격을 만들려고 빈 문단이나 연속 br을 넣지 않아요. 화면을 바꾸거나 요약 너비를 조절한 뒤에도 수식이 읽혀야 해요.

## 원자료 충돌

원문 오타·참고 답 오류를 몰래 수정하지 않아요. 카드의 답안지(정답·풀이), 기출 합본(`23, 24 소스/N강 합본.pdf`), 웹과제(`웹과제/N장/questions.json`), `.pack/key-check.md`의 정답 대조가 서로 다르면 disputed로 남기고 조건과 다른 해석을 밝혀요. `.pack/key-check.md`나 `.pack/question-audit.md`에 보류·모호로 적힌 문항도 같은 방식으로 다뤄요. 두 파일은 일부 팩에만 있어요. 없으면 `.pack/variants.md`의 `의도한 정답과 이유` 열과 대조하고, 파일이 없다는 것만으로 disputed로 두지 않아요. 교과서·강의노트·STT·정리노트의 설명이 충돌할 때도 disputed로 남겨요. 실제 자료를 필요한 범위에서 읽고 자료/쪽을 기록해요. 

원자료 충돌은 두 경우로 나눠요.
- (A) 충돌: (C)에 해당하지 않으면서 카드 정답이 인쇄 답안지·기출·웹과제·key-check 판단 답 또는 독립 재풀이 답과 다르면 disputed로 남기고 그 팩은 발행을 보류해요.
- (B) 결함 공개: 카드 정답이 인쇄 답·key-check·독립 재풀이와 모두 같고 문항 표현만 결함(다른 보기도 논쟁 여지, 방향·가닥 누락, 오타)이면 설명을 써요. understand에 `<strong>문항 결함:</strong>` 한 줄을 넣고, solve에서 논쟁 보기를 정직하게 판정해요("엄밀히는 맞을 수도 있어요 — 이유"). pitfall에는 시험 대처를 적어요. content 검토는 공개가 정확한지 확인해요. 이 경우는 disputed가 아니에요.
- (C) 인쇄 정답 오류: 카드 정답이 기출 인쇄 정답과만 다르고, 교과서·강의노트 근거와 독립 재풀이 답(있으면 key-check 판단 답)이 모두 카드 정답과 같으면 설명을 써요. understand에 `<strong>인쇄 정답 오류:</strong>` 한 줄로 인쇄 정답과 카드 정답을 함께 밝히고, solve에서 인쇄 정답 보기가 왜 틀렸는지 근거 쪽과 함께 판정하고, pitfall에 시험에서 인쇄 정답을 만났을 때의 대처를 적어요. 이 경우는 disputed가 아니에요.

## forecast 예상문제

명시 경로의 예상문제는 p1–p15 전체를 다루고 o1·o2 개요는 제외해요. 해당 버전 src/v<K>/pack.json과 blueprint.md의 기출 출처·모드·노트 앵커를 확인해요. key-check.md/variants.md 대신 이 근거를 사용해요. 원문 그대로인 문항만 원문 답과 직접 대조하고, 변형 문항은 바뀐 조건·숫자·보기 순서로 실제 재풀이해요. 새 예상문항을 실제 기출로 표현하지 않아요. original이 새 예상문항의 출처 안내이면 기출 원문이라고 주장하지 않아요.
