# 검토 기록과 발행

검토 에이전트가 읽는 문서예요. 컨트롤러(메인 에이전트)는 이 파일을 읽지 않아요. 검토 결과는 검토 JSON과 `evidence/`에 쓰고, 컨트롤러에는 SKILL.md 「컨트롤러 컨텍스트와 보고 계약」의 영수증만 돌려줘요. 문항별 표나 근거 문장을 보고 본문에 싣지 않아요. fail 항목의 고칠 지시는 `evidence/<종류>-fixes.tsv`에 써요.

기계 검사는 구역·소문항·수식 보존·자원·파일 해시를 검사해요. 의미와 답이 맞다는 판단은 하지 않아요. build가 만든 `review.json`은 전부 `not_run`이에요. 실제 확인을 수행한 에이전트만 기록을 갱신해요. 기출 합본 PDF·웹과제·교과서의 문항 쪽과 대조하고, 카드의 원 답안을 독립 검산의 결과로 간주하지 않아요.

JSON의 `input_hash`는 현재 원본과 설명 조각에 묶여요. build 출력의 `artifact_hashes`도 그대로 검토 대상이에요. 조각·원본·렌더링 파일을 바꿨다면 다시 build하고 검토해요. 예전 검토 보고서는 통과하지 않아요.

- `source_visual`: 문항 조건·보기·그림·소문항을 원자료의 실제 쪽과 대조. 기출 문항은 `23, 24 소스/N강 합본.pdf`의 해당 쪽, 웹과제 문항은 `웹과제/N장/questions.json`의 해당 항목, 교과서 그림·표를 옮긴 문항은 `교과서/생명과학_기초와_응용_2판/0N장_*.pdf`의 해당 쪽. `data-source="생성 변형 …"` 카드는 `.pack/variants.md`에서 같은 id 행(근거 토픽, 형태 열의 교재 쪽)과 그 근거 토픽의 정리노트 절, 교재 쪽이 적혀 있으면 그 교과서 쪽과 대조. reviewer와 evidence에 자료/쪽/대조 결과.
- `content`: 상위 status/reviewer/evidence 및 items의 모든 `pN:a` 또는 `pN:main`. 아래 **판단 기준과 선지 대응 검토**를 수행하고, recall의 문제 단서·용어와 기호의 뜻·적용 조건, 모든 답·검산·충돌 여부를 확인해요. 필수 구역은 understand/recall/solve/verify이고 start/pitfall/retry는 별도 도움이 있을 때만 있어야 해요. 선택 구역이 없다는 이유로 실패시키거나 채우지 않아요. 문항 결함·인쇄 정답 오류에 필요한 pitfall 대처는 유지해요. 표현 결함이 있는 문항은 보기별 조건·유보가 verify와 sum에도 남는지, 출제 의도상 분석 답을 엄밀한 유일 정답으로 단정하지 않는지, 공식 답 확인 여부가 understand·solve·verify·pitfall·sum에서 일관적인지 확인해요. 정상 문항에 불필요한 모호성 문구를 요구하지 않아요.
- `independent`: 같은 모든 items, method=`exact|symbolic|numerical|proof|qualitative`, conclusion과 evidence. 저작 에이전트와 다른, **정답을 보지 않은** 별도 에이전트가 문항(지문·보기·그림)과 정리노트·교과서·강의노트만으로 다시 풀어 카드 정답과 일치해야 해요. 이 에이전트에게 카드의 정답·풀이·설명 조각을 주지 않아요. method는 주로 `qualitative`, 유전 교배 비율 같은 계산은 `exact`예요. 컨트롤러는 재풀이 답을 카드 정답과 `.pack/key-check.md`의 인쇄·판단 답에 대조하고, 하나라도 다르면 disputed로 둬요(충돌). 카드 정답이 이 답들과 모두 같고 문항 표현만 결함이면 disputed가 아니라 설명에서 결함을 공개한 것으로 보고, content 검토에서 공개가 정확한지 확인해요. key-check.md(또는 question-audit.md)가 없는 팩은 카드 정답과 `.pack/variants.md`의 `의도한 정답과 이유` 열에 대조하고 evidence에 "key-check 없음"을 기록해요. 파일이 없다는 것만으로는 disputed가 아니에요. 재풀이 기록(`evidence/independent-<range>.md` 등)과 자료 쪽을 구체적으로 기록. 단, 카드 정답이 기출 인쇄 정답과만 다르고 교과서·강의노트 근거와 독립 재풀이(있으면 key-check 판단 답)가 모두 카드 정답과 같으면 인쇄 정답 오류로 보고 disputed로 두지 않아요. 이때 설명의 `<strong>인쇄 정답 오류:</strong>` 공개와 근거 원리를 content에서 확인하고 상세 자료·쪽은 evidence에서 확인하고, evidence에 인쇄 정답·카드 정답·근거를 함께 기록해요.
- **문항별 개념 링크:** 모든 profile에서 각 문항의 recall에 정리노트의 실제 개념 앵커 링크가 있는지 확인해요. content는 연결된 절을 읽고 문제의 판단 기준을 설명하는지 문항별 evidence에 적어요. browser는 링크를 실제로 눌러 파일과 목표 절로 이동하는지 확인해요. 대응 절이 없는 문항은 recall의 `data-note-link-omitted` 사유를 확인하고, `content.note_link_exceptions`에 정확히 그 문항 ID만 기록해요. 각 항목의 `reason`은 조각의 사유와 같아야 하며 `status: pass`·`reviewer`·`evidence`가 필요해요. build가 만든 `not_run`을 근거 없이 승인하지 않아요. 링크 없는 문항의 예외 미승인·빈 사유·사유 불일치·불필요한 예외 항목은 발행을 막아요. 예외 없는 팩은 빈 객체를 유지해요.
- `browser`: 우측 요약 패널을 열었을 때 고정 제목 다음에 요약부터 표시되고 중앙 문항 제목이 반복되지 않는지, 문항 전환 뒤에도 같은지 확인. 1280×900 및 375×812, light/dark. 모든 문항의 목차·이전/다음·요약·수식·표·그림·링크를 확인. 콘솔·KaTeX 오류·누락 자원·문서 가로 넘침은 0. 짧은 인라인 수식의 스크롤 컨테이너와 수식 영역의 보이는 스크롤바는 0. 구역 24px·제목 아래 12px·소문항 16px 간격, 행렬 잘림과 겹침을 실제 렌더링으로 확인. 긴 수식은 의미 단위 줄바꿈을 우선하고, 더 나눌 수 없는 긴 수식만 안내와 함께 스크롤바 없는 국소 이동을 허용. 외부 요청 없이 로컬 자원으로 렌더링. 1280·1024에서 본문 왼쪽 문제 패널이 기본으로 열리고 목차와 동시에 열리는지, 원문 탭 전환(원문 없는 문항은 원문 탭 숨김)과 오른쪽 요약 패널 열기가 되는지, 문제 패널 세 방식 전환(왼쪽·오른쪽 붙이기·띄우기, 오른쪽일 때 문제·요약 동시 열림)과 띄운 창 이동·크기 조절·화면 안 clamp가 되는지, 375에서 '문제 보기' 토글이 해설 위에 있는지 확인. 보기 문항의 판정 문단이 보기별 회색 카드로 보이고 결론 문단은 카드 밖인지, 문항마다 오답을 눌러 판정 표시·상단 알림·보기 스크롤과(넓은 화면) 해설 판정 문단 이동을, 다시 풀기 뒤 정답을 눌러 정답 표시를 확인하고, 문제 그림은 눌러 확대되는지 확인.
  - **표준 스크립트:** `mpe_cli.py browser --run RUN --shots`가 1280×900·1024×768·375×812 × light/dark에서 모든 문항의 hash 이동, 문제 패널(넓은 화면)·'문제 보기' 토글(좁은 화면), 원문 탭 표시 여부, 오답 → 판정 표시 → 다시 풀기 → 정답 표시, 요약 패널 제목과 문항 제목 비반복, KaTeX 오류·콘솔 오류·로컬 4xx·외부 요청·가로 넘침, 정리노트·원 문제 링크의 파일과 앵커(발행 폴더 기준으로 디스크에서 확인)를 검사해요. 결과는 `evidence/explain-browser.json`이고 stage에 자동 동기화돼요. 스크립트가 보지 않는 간격·겹침·행렬 잘림·패널 세 방식 전환·띄운 창·그림 확대는 스크린샷과 필요한 화면만 직접 확인한 뒤 `review-merge --kind browser`로 기록해요. 1024에서 요약 패널을 열면 `fit()`이 목차 패널을 자동으로 닫는 것은 정상이에요(목차 클릭 대신 hash로 이동해요).

## 출처 표시 검토

해설 본문·표·그림 설명·요약과 대응 MD에서 교재·교과서·강의노트의 장·쪽·그림 번호 출처가 생략됐는지 확인해요. 혼합 괄호에서는 학습 설명·조건·영어 용어·수식·수업 밖 보충 안내가 남아야 해요. 원 문제·원문 탭·관련 정리노트 링크와 내부 해설 조각·evidence의 출처는 보존해요. 내부 조각을 보존한 표시 정리에서는 content·independent의 입력이 같음을 먼저 확인하고, 변경된 HTML·MD의 문장·원문 보존과 화면을 실제 검토해요. 과거 검토에 새 해시만 덮어써 승인하지 않아요. 기존 발행분의 표시만 직접 정리한 경우에는 원 manifest·validation을 당시 발행 기록으로 보존하고, 변경 전후 HTML·MD 해시·원문/마크업 보존 대조·현재 화면 검사 결과를 `evidence/display-citations-YYYYMMDD.json`에 별도로 남겨요. 이 기록은 현재 자료로 네 검토를 다시 수행한 발행 승인이 아니에요. 정규 재발행은 기존 build/check/review/publish 계약을 따라요.

## 판단 기준과 선지 대응 검토

객관식의 모든 선지에 대해 `문항/소문항 | 선지 | 실제 주장 | 적용 기준 | 적용 결과와 판정 | 근거 위치`를 evidence에 기록하고 content items의 evidence에서 가리켜요. ㄱㄴㄷ형은 개별 진술과 조합 보기의 대응을 모두 확인해요. 정답 선지도 생략하지 않아요.

1. **기준의 사용 가능성:** recall이 이름·정의만 나열하지 않고 학생이 무엇을 확인할지 알려 주는지, 필요한 뜻·이유·적용 조건이 있는지 확인해요. 기준이 선지 내용을 반복하거나 정답을 알고서만 적용할 수 있으면 수정해요. 필요조건을 충분조건으로 바꾸거나 서로 다른 판단에 한 기준을 강요하지 않아요.
2. **선지와 근거의 대응:** 원문의 라벨·실제 표현을 해설과 한 쌍씩 대조해요. 예를 들어 ‘리보솜에서 전사 개시’라는 선지에 ‘주형 가닥은 하나’라는 설명을 붙이면, 두 문장이 각각 사실인지와 관계없이 근거 불일치로 실패예요. 올바른 답 글자만으로 통과시키지 않아요.
3. **기준에서 판정까지:** 각 선지에 기준을 어떻게 대입했는지, 왜 선택·제외하는지 확인해요. 진술형의 참·거짓과 용어 선택형의 사례 적합성을 구별하고, 부정형은 질문 방향을 다시 대조해요. ‘모두 맞다/해당 없음’은 다른 선지 판정의 결과로, ㄱㄴㄷ형은 진술 판정 후 조합으로 도출해야 해요.
4. **필요한 내용만 유지:** 지워도 기준 이해·선지 판정·오류 방지에 손실 없는 문장, 구역 간 복제, 일반적 당부, 쓰이지 않는 배경지식은 삭제·통합해요. 초보자에게 필요한 개념과 근거 원리·조건·가정·결함 공개는 남겨요. 자료 위치 출처는 evidence에 보존하고 독자용 해설에서는 생략해요. verify는 별도로 확인한 내용이 있어야 하고, sum은 본문과 일치하는 핵심 기준·결론만 짧게 남겨요.

하나라도 미해결이면 해당 content item을 fail로 남겨 발행을 보류해요. 기계 통과는 이 의미 검토를 대신하지 않아요.

명칭·단위 요구는 [공통 기준](../../bio-review-pack/references/note-feedback.md)과 원천의 실제 문장으로 검토해요. 원문의 이름을 보존하고 recall의 대응과 solve의 판별 경계가 근거에 있는지 확인해요. 자료에 없는 동의어는 넣지 않아요. 개인 미확인 가설을 일반 사실로 단정하거나 해설 공개 뒤의 성공을 독립 회상으로 보고하면 수정해요. independent에게는 설계 정답·정답키·저작 설명 조각을 전달하지 않는 기존 계약을 유지해요.

네 검토 source_visual·content·independent·browser는 `lite`에서도 모두 실제로 수행해요. 각 단계와 items는 status=`pass`, 비어 있지 않은 reviewer/evidence여야 발행돼요. `not_run`, `fail`, `disputed`는 발행을 보류해요. numerical은 유한한 tolerance>0, 0<=residual<=tolerance도 필요해요. proof에 숫자 예제 확인만 있는 evidence는 수동 검토에서 승인하면 안 돼요.

```json
{
  "status": "pass",
  "reviewer": "독립 검산 에이전트(정답 비공개)",
  "evidence": "evidence/independent-1008.md: 정리노트·교과서 05장 p.NN으로 다시 푼 답 (5), 카드 정답·key-check.md 판단 답과 일치",
  "method": "qualitative",
  "conclusion": "보기 (1)~(4)는 교과서 설명과 일치하고 (5)만 틀려 답 (5)"
}
```

사용한 근거 파일은 대상 작업 디렉터리의 `evidence/` 아래 보관해요. `references`에는 읽은 저장소 내부 자료의 절대 path와 SHA-256을 기록해요. 발행 직전 재확인돼요. `artifact_hashes`에는 manifest를 포함한 현재 stage 파일의 상대경로→SHA-256을 기록해요. build가 넣은 값을 승인 전 점검하며 임의로 오래된 검토에 새 해시만 덮어씌우지 않아요.

답 충돌·조건 모호함·원문 미확인은 해당 팩을 disputed로 표시하고 이유를 보고해요. 다른 독립 팩은 통과하면 발행할 수 있어요. 기존 파일은 변경하지 않고 설명 소유 파일만 백업 후 교체하며 실패 시 복구해요.

## forecast 예상문제

명시 경로의 예상문제는 p1–p15 전체를 다루고 o1·o2 개요는 제외해요. 해당 버전 `웹과제예상/<N>장/.pack/v<K>/`의 pack.json과 blueprint.md의 기출 출처·모드·노트 앵커를 확인해요. key-check.md/variants.md 대신 이 근거를 사용해요. 원문 그대로인 문항만 원문 답과 직접 대조하고, 변형 문항은 바뀐 조건·숫자·보기 순서로 실제 재풀이해요. 새 예상문항을 실제 기출로 표현하지 않아요. original이 새 예상문항의 출처 안내이면 기출 원문이라고 주장하지 않아요.

독립 검산은 별도 에이전트가 정답을 보지 않은 문항 사본으로 수행해요. 설계표의 정답·pack.json 정답키·o1/o2 정답·카드 풀이·해설을 제공하지 않아요. 예상 스킬 7단계 블라인드 리뷰어가 이 조건을 이미 만족하므로, 그 ledger를 `mpe_cli.py import-blind --ledger`로 independent 항목에 승계해요. 승계는 카드 SHA-256이 블라인드 당시와 같고, p1–p15 모두 블라인드 답이 answer_key와 같고, 이의가 없을 때만 돼요. 하나라도 어긋나면 거부되고 별도 독립 검산자가 다시 풀어요. 승계 기록은 `evidence/independent-blind.md`와 `evidence/blind-ledger.json`이에요.

forecast의 source_visual은 p1–p5 기출 카드의 기출 합본 해당 쪽만 렌더해 대조하고(최대 5쪽), 예상 스킬 6단계 check.py 원문 대조(`[exam-verbatim]`·`[exam-twin]`·`[exam-number]` 통과)를 evidence에 함께 적어요. 새 예상문항 p6–p15는 blueprint 노트 앵커의 정리노트 절과 텍스트로 대조하고, 교과서·강의노트 PDF는 그 문항이 교과서 그림·표를 옮긴 경우에만 해당 쪽을 렌더해요. 컨트롤러가 재풀이 결과와 pack.json/blueprint.md를 대조하고 자료의 path/SHA-256을 references에 기록해요. 오류가 남으면 disputed/fail로 두고 [연결 계약](../../bio-webquiz-forecast/references/explanation-handoff.md)에 따라 수정 후 다시 검토해요. 해설만 수정하면 build/check 및 네 검토, 문제/문맥 변경이면 새 RUN 재추출부터 수행해요. 최초 이후 최대 2회 수정·재검토를 넘기면 발행을 보류해요. 상태나 해시만 바꿔 승인하지 않아요.

## 시험 예상 입력

exam profile은 75문항(객관식55/단답20)을 모두 검토한다. 단답형 canonical/accepted/case_sensitive를 원문·해설·MD에서 대조한다. 낯선 답의 자기채점과 단위·대소문자 판정을 확인한다. 시험 `.pack/vK/source-manifest.json`의 present/missing 상태도 현재와 같아야 한다. 문제 검토 pass는 해설 네 검토를 대신하지 않는다. 문제/해설의 수정 예산 최대2회는 같은 시험 RUN에서 관리한다.
