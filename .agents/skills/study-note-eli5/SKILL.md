# Study Note ELI5

A normal invocation must produce a complete guide. Do not hand off a draft or
selected-question sample as the requested result.

## Files

ELI5 artifacts are organized under `정리노트/eli5/`, MMDD = the session date.

- `정리노트/eli5/src/MMDD/guide.py` (+ sibling modules): the guide data. This is the
  only hand-edited source. `eli5/src/0910/` is the worked example.
- `정리노트/eli5/MMDD-eli5.html`: generated by scripts/build_guide.py.
- `정리노트/eli5/meta/MMDD-eli5.coverage.json`, `MMDD-eli5.question-scope.json`:
  metadata generated by scripts/build_guide.py. Never edit them by hand.
- `정리노트/eli5/meta/MMDD-eli5.question-scope-overrides.json`: evidenced status changes, if any.
- Test fixtures sit under `tests/fixtures/study_guide/` (e.g. `0910-eli5-audited.*`).
- Older drafts and exploratory variants sit in `정리노트/eli5/archive/`.
- build_guide.py refuses to overwrite an HTML that lacks its coverage JSON.

## Workflow

1. Read the note and companion quiz completely. Inspect original PDFs
visually when wording, choices, diagrams, format, or answer-key color is
uncertain. Do not trust the companion quiz's options over the originals. Read
references/coverage-contract.md.

2. Lock the question universe, phase 1: run scripts/build_question_scope.py
on the note with `--overrides` and no audits, writing
`MMDD-eli5-complete.question-scope.json`. This fixes included, review, and
deferred IDs only. Inspect every source question. Change a status only
through an evidenced override; never delete an ID.

3. Inventory facts in the data module with guide_kit.F. Put every nonblank
note line in a block, and split teaching content into independently
checkable facts that keep conditions, quantities, units, directions,
warnings, and exceptions. Process steps need location, input, and output
dimensions. A fact a question needs but the note lacks (lecture PDF, STT,
previous note, original figure) goes in a supplement or review block. If no
note line fits it, use an external block with no start/end whose facts cite a
reference source.

4. For every included or review question, write guide_kit.Q with the
original wording, options, and order. Also record the printed key, the
guide's answer, grading, requirements (fact IDs), a diagnosis for every
option or a rubric, and any disclosed conflict. Add also_accept for ambiguous
items and fig for diagram-dependent items. Deferred questions get a concrete
reason, a later prerequisite, and fact IDs.

5. Write concept sections with guide_kit, in this order: analogy (label who
made it and state its limits), accurate diagram, mechanism, conditions and
exceptions, a ⚠️ box, then 1–3 recall prompts. Mark every taught fact with
T(id, "fact ids", html). Run scripts/build_guide.py on guide.py. It writes
the HTML, the coverage JSON, and the phase-2 audited scope lock. Fix every
build error without deleting facts or shrinking scope.

6. Run verify_guide.py with artifact, coverage, scope, and phase draft.

7. Review with reviewers who did not write the solutions (e.g. subagents):
- Solvability: run scripts/make_blind_copy.py and give only the blind copy
  to a reviewer told not to open any other file. It answers every active
  question from the teaching text and lists gaps. Fix gaps in the teaching,
  not in the solutions.
- Source and reverse audit: check note → guide for omissions and
  distortions, guide → sources for unsupported or overstated claims, and
  the question transcription against the originals.
- Visual: check desktop, and mobile under a real 375px emulation. A headless
  `--window-size` under about 500px renders wider and fakes overflow. Check
  print with headless Chrome `--print-to-pdf`, confirming that the solutions
  print expanded. Look at every SVG.
- Any change to the artifact after a review invalidates that review. Rerun
  the blind check on the final artifact.

8. Record the review in the coverage JSON, bound to the current artifact and
inventory hashes. Then run the same verifier with phase complete. Hand off
the normal result only when it passes. Report question counts, corrections,
ambiguous items, and semantic/visual review separately from machine
validation.

## Partial requests

Only an explicit user request for a subset permits partial delivery. Set
output_stem to `MMDD-eli5-partial` and delivery_mode=partial, invoke draft
validation with allow-partial, display a visible PARTIAL banner, and list
omitted IDs. Never describe it as complete, and never use it to satisfy an
ordinary request to use this skill.

## Output contract

Return a short Korean summary and direct local-file link only for the requested
delivery type. For complete output, state exact included, review, and deferred
counts plus disclosed conflicts and the final complete validation result.
